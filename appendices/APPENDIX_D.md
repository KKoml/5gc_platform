# Appendix D.1–D.2. Association, alignment and data-product construction

## D.1 Session association and temporal aggregation

[PROCESSING_LINEAGE.csv](../tables/PROCESSING_LINEAGE.csv) binds source records, processing programs/versions, rules, outputs and field ranges. Each pinned file hash is in `manifests/SOURCE_FILES.csv`; the later repair program has a separate source/published hash record. Source acquisition, offline export and model-input construction are different stages.

**Session association.** `export_session_map.py` recognizes the SMF `SessionMap` extension and older context lines, normalizes timestamps, and joins evidence within a default 15 s correlation window. SUPI and PDU session ID supply the session identity; DNN/S-NSSAI, UE IP, selected SMF/UPF and TEIDs support attribution. Session IDs can repeat across UE contexts or time and IP/TEID can be reused. Direct log evidence and address/deployment fallback retain different provenance (`label_source`/source path), and unresolved fields remain null. The sample has `selected_amf=null`; this is not filled merely because the deployment is known. No source implies full current per-instance UE ownership counts.

**Packet/flow processing.** `parse_pcap.py` uses tshark-derived packet fields and creates capture-family flow/summary/time-series products. N3/N4/N6/SBI and remote UPF captures remain different observation points; duplicated traffic must not be blindly summed. N6 logical-flow handling and session mapping attach entities where evidence supports them. Packet timestamp/length, five-tuple, TEID and first/last-seen have different granularities. Some saved flow first/last-seen strings omit a UTC offset and reflect the decoder/local-time convention; they are preserved as original strings in the examples. Their timezone must be bound through the original run/decoder context before a cross-source UTC join, rather than assuming that the displayed strings are UTC. Captures use the saved 256-byte snap length; observed packet length versus saved capture length must be distinguished.

**Base time alignment.** `export_model_timeseries_csv.py` computes UTC bucket boundaries by flooring epoch seconds to the chosen bucket size, initializes the span from observed minimum/maximum timestamps, counts events and combines asynchronous source values. Original timestamp/age metadata are retained where supported. Its `apply_snapshot_series` holds the last snapshot in subsequent buckets; a regular 1 s output does not establish 1 s raw sampling or a new physical measurement. Event increments, state snapshots and complete-flow-derived interval quantities must not all be described as the same interpolation operation.

The historical exporter uses completed flow first/last times, total duration and bytes to allocate some flow quantities across intersected buckets. That is an offline summary; the flow's final record may include information unavailable at an earlier forecasting cutoff. Run-level splitting or training-only normalization cannot repair sample-construction leakage. This is why the unchanged historical 81-column product and later prefix-limited task views are separately named.

**V3 formation.** `export_v3_timeseries.py` reads model buckets, saved plan, actual Core/access timelines, manifest and gate evidence, then emits exactly `V3_COLUMNS` from `v3_schema.py`. N3/N4 fallback and UPF-interface substitutions have explicit coverage provenance. Planned and observed intervention windows remain distinct. Formal paired validity depends on actual overlap and recovery/quality constraints, not merely a planned flag. Final quality audit can refresh V3/gate output; it does not retroactively alter raw observations. The published sample is selected from the existing source table, not reconstructed from copied excerpts.

**Business aggregation.** The base exporter computes a 60 s terminal-outcome window with at least twenty outcomes and exports gold, silver and aggregate sidecar results. Completion is success / (success + failure), with timeout/error treated as terminal failures. Low-sample windows remain empty and are not carried forward. This rule differs from recovery gating (minimum fifteen per tier/window, two windows and guard). The run-wide transfer summary is not a dynamic time-series replacement.

`export_per_nf_timeseries.py` creates per-NF products. Its session/UE associated sets are cumulative additions in the frozen implementation; they must not be interpreted as contemporary active-user ownership. Other communication, session-recovery and report products have their own schemas and should not be forced into the 81-column contract.

## D.2 Quality checks, separate task builders and handoff

The run quality, long-run stability, 24 h endurance, prediction-readiness, transfer and provenance checks are separate verdicts. An accepted campaign member does not imply every later task is causal, every field is measured, every packet was captured, or every remote reviewer can access the files. Recomputed coverage checks compare actual cells to metadata. The release verifier checks the publication itself—syntax, schema, sample linkage, hashes, privacy and file size—without starting the platform.

The current platform dictionary is a later working-copy capability inventory with `kpi-dictionary/v2`. It includes optional later domains; its count of 400/215 is verified but historical equivalence to the paper's exact dictionary is not established. Published source hashes and the evidence copy preserve its original semantics. No field role, measured value or source-table column was changed to obtain 32 or 24.

**Core24.** The existing Core-side candidate records 24 explicit variables, mapped to `metrics/nf-resource.jsonl`, `metrics/host-resource.jsonl`, `metrics/interface-resource.jsonl` and `metrics/nf-state.jsonl`. Its six interface variables are on `upfgtp-silver` in the current candidate, not six independent interfaces or both UPF interface streams. Source-name matching is semantic evidence only. The final experiment-machine manifest must specify its input file hashes, exact builder/version, timestamp/grid policy, masks, carry-forward tolerance, reset handling and conversion rules. These are not asserted from a task README or a numerical match. The 5 s candidate is not described as direct 81-column selection/resampling.

**Prediction repair.** The Core-side repair artifact `w1-future-leakage-fixed-task-views.v1` rebuilds task histories from raw prefixes strictly before each sample cutoff and computes targets in separate target intervals. It recalculates N6 bitrate, RTT proxy, jitter and loss-related fields for task views, without changing the raw records or old 81-column tables. The complete repair program and Core-side D06 output manifest are included with distinct provenance. They support source matching, not a claim that this artifact is the final experiment-machine input. Event times, masks, repaired target names and actual tensor files must be matched when that machine uploads its authoritative manifest.

**Required handoff.** `handoff/EXPERIMENT_MACHINE_MANIFEST_TEMPLATE.csv` names the required run, relative path, content hash, time range, fields, producer/version, transformations and source hashes. `handoff/README.md` gives the join/check procedure. Each final prediction/Core24 file must match the seven accepted run identities and record every conversion. Whole-run splits, gaps, original masks and normalizer-fit scope remain the experiment-machine responsibility. This publication reserves `experiment-machine/` and does not invent missing models, settings or scores.

**External raw delivery.** Complete raw files remain on the data machine and are listed only. Existing recorded hashes are preserved with their verification status; source files lacking recorded hashes remain unresolved. Cloud upload is performed separately by the owner. After cloud URLs and the experiment-machine manifests arrive, verify anonymous retrieval and hashes, then update the handoff index. No model result or raw-file availability is promoted from planned to delivered.
